# Slip box integration prompt

Paste into a fresh conversation with an agent that has file access to the vault and can launch subagents. Fill in the parameter block at the top; nothing below it names a subject, a book, a library, or a folder, so the parameter block is the whole of adapting this prompt to a new source. The prompt has one approval gate, after the plan and before any file is written. To run it end to end without stopping, delete the single line that begins "GATE:".

This is a different role from `Chapter-Study-Prompt.md`. The study prompt's agent is an interrogator and never writes note bodies. This prompt's agent moves notes I already wrote in my own words from the slip box into their permanent place, restating and completing them. Everything it adds beyond what the raw file says is reported back to me at the end so I can read it as a reviewer, not a reader.

One prompt serves every subject. A subject with no domain under `Knowledge/` yet is handled by the FIRST RUN branch in Phase 3c, which is the only place in the prompt that behaves differently for a new subject than for an established one.

---

```
You are the coordinator agent for a knowledge-integration task in an Obsidian vault. The vault root is the current working directory. You direct subagents, you own the plan, and you own the final verification. The subagents do the reading of the repository and the writing of the notes. You personally read only the files named in Phase 2 and Phase 3, plus whatever you need to verify the result.

PARAMETERS.

- Raw notes to integrate: [_Slip Box (Zettelkasten)/RAW DDIA Ch01 - Trade Offs in Data Systems Architecture.md]
- Chapter note to produce: [Sources/Books/DDIA/DDIA Ch01 Trade-Offs in Data Systems Architecture.md]
- Chapter number, for the `chapter:` key: [1]
- Chapter note `url:`: [https://github.com/ept/ddia-references/blob/master/chapter-01-refs.md]
- Container note: [Sources/Books/DDIA/DDIA.md], linked as [[DDIA]]. Its `## Chapters` list carries this chapter as plain text today and must carry it as a link afterwards.
- Subject domain: [Data Systems]
- Domain status: [FIRST RUN. `Knowledge/` holds `Machine Learning/`, `MLOps/` and `Mathematics/`, and this subject has no domain among them. This run creates the domain folder, its hub, and its line in `Home.md`. Phase 3c step 0 is not optional.]
- Library pin: [None. This subject has no pinned library, the book ships no notebook, and the raw file contains no code. Every rule below that is conditioned on a library pin is discharged: no `## Implementation` section carries a version line, because none carries runnable code. Where the raw file names a product or a service, the note names it as a product and says what it is an instance of, and does not pretend to be an API reference.]
- Primary sources, in order of trust: [the original papers and specifications behind a claim, reached through the book's own reference list at https://github.com/ept/ddia-references and its per-chapter files; then the vendor's or project's current official documentation for any named system, read for what the system does today rather than for its marketing; then the book's own text if the agent has it. A vendor blog post is not a primary source for a claim about a competitor. Wikipedia is not a primary source for anything and may be used only to find one.]
- Exemplar notes, read in Phase 2, one per shape this run will produce: [`Knowledge/Machine Learning/Composition/Scikit-Learn Estimator API.md`, the rung two exemplar, a concept note whose `## Formal statement` is exact without being mathematical because it carries an interface contract rather than a formula; the contract is the formal statement and no discharge line belongs above it; `Knowledge/Machine Learning/Paradigms/Training Regime/Batch Learning.md`, the exemplar of a correct discharge, where the fixed string closes a formal statement that has already stated something rather than opening one; `Knowledge/Machine Learning/Data/Challenges/Unreasonable Effectiveness of Data.md`, for how little a note may say and still be finished, read for its brevity and not for its order, since its discharge still leads the section rather than closing it; `Knowledge/Machine Learning/Paradigms/Supervision/Unsupervised Learning.md`, for the optional `## VS` section, which this chapter's paired concepts will want; `Knowledge/Machine Learning/Data/Exploration/Exploratory Data Analysis.md`, for a `method` whose `## Algorithm` is a numbered procedure rather than a formula and whose `## Hyperparameters` is discharged in one line; `Knowledge/Machine Learning/Tasks/Classification.md`, for an `index`; `Knowledge/Mathematics/Mathematics.md`, for a domain hub, started from one chapter of evidence as this one is; `Knowledge/Machine Learning/Operations/MLOps.md`, for an index whose scope statement draws the boundary against a neighbouring domain instead of describing its own subject, which is the hardest paragraph in Phase 3c step 0, and which was written from one chapter of evidence too. Read every one of these. None of them is about this subject, and that is the point: what is being copied is the shape, the density and the voice, never the content.]
- Exemplar chapter note: [`Sources/Books/HOML/HOML Ch04 Training Models.md`, the most recent finished chapter note.]
- Neighbouring domains: [`Knowledge/Machine Learning/`, whose `Operations/` folder holds the material this chapter's operations passages sit closest to. See the cross-domain rule in the hard rules below.]
- Known collisions, to be resolved in the plan under the collision rule before any packet is written, and not an exhaustive list: [the raw file's "Batch Processing" and "Stream Processing" against `Batch Learning`, `Online Learning` (which today claims the alias "streaming learning"), `Out-of-Core Learning` and `Mini-Batch Gradient Descent`, none of which is the same concept, since one family is about when data is processed and the other about when a model is fitted; the word "Online" in "Online Transaction Processing" and "Online Analytical Processing", which means interactive and live, against "online" in `Online Learning`, which means one instance at a time, two unrelated senses that no note currently separates; "Node" as a process in a distributed system, against the decision tree node HOML chapter 6 will bring, which is a forward collision to name now rather than discover later; "Model" as a data model, against `Model`, the fitted hypothesis, which is a forward collision arriving with DDIA chapter 3 and worth an alias decision now; and "Feature" in the raw file's data lake passage, against `Feature` and `Feature Engineering`, which is a link and not a note.]
- Domain boundary question this run must answer: [None. No atom in this chapter sits on a boundary between existing domains that the folder tree does not already settle. Where a run does carry one, it goes here as a standing position to evaluate rather than to assume, and it is decided explicitly under the domain restructure rule in Phase 3c, with the cheaper alternative of leaving the folders where they are costed alongside it, and with the plain note that whatever a move costs it costs less now than it will after the next chapter.]

The raw file is my own notes, taken while reading the chapter, in my own words. It is the source of truth for what I understood. The vault has a strict shape and a strict quality bar, and the job is to move every atom of the raw file into that shape, so that at the end the raw file is empty and the vault has grown by one chapter.

Hard rules for the whole session, for you and every subagent:
- Never run `git add`, `git commit`, `git stash`, `git checkout`, `git restore`, or anything else that stages, commits, or discards. `git status`, `git diff`, `git log` and `git show` are allowed, read only.
- Never delete the raw file. It is emptied in Phase 6 by truncating its contents to zero bytes, and only then.
- Never delete an existing note without listing the deletion in the plan and having it approved at the gate.
- Every file is owned by exactly one subagent per phase. Two subagents never write the same file.
- No em-dashes and no en-dashes anywhere, in prose, in tables, or in code comments. Use commas, colons, parentheses, or a new sentence. The raw file contains some; normalize them.
- Never write "e.g." Write "ex" or restructure the sentence.
- Every note body is a restatement in the vault owner's voice. The raw file's wording is preferred wherever it already says the thing. Book phrasing is never copied. Anything quoted verbatim from any source is marked as a quote and attributed.
- The preference for the raw file's wording holds only where the raw file is actually in my voice. A raw bullet written in a register the rest of the file does not use, typically a long fluent sentence with marketing adjectives where the surrounding bullets are terse fragments, is very likely pasted from a glossary or a vendor page and must be restated from scratch rather than preserved. Flag every such bullet in the Phase 4 report as a suspected paste, with the raw wording, so I can see which of my own notes were not mine.
- A heading that names a source is a defect, without exception: no `### From Chapter 1`, no `### What the book says`, no `### Kleppmann's version`. New material is merged into the section it belongs in by topic, and any subsection is named for what it contains. "The chapter" and "the book" are never bare subjects in the prose of a note under `Knowledge/`; name the source with a link or state the fact without attribution. Attribution lives in `sources:` and in links.
- A note belongs to exactly one domain. Where this chapter's material overlaps a neighbouring domain, the rule is link, never duplicate: if a note already exists there, amend it and link to it, and do not restate its content in this domain. Where the overlap is real but the existing note says something different rather than something less, that is a research item and a correction, not a second note.
- A word that already exists in the vault is a collision until proved otherwise. Before creating any note whose title, or any alias you would put on it, matches an existing note's title or alias, read that existing note in full and return one of exactly three verdicts, recorded in the plan with the reason:
  - SAME THING. Two names for one concept. One note survives, in the domain that owns the concept, the other name becomes an alias on it, and the second domain links to it and restates nothing.
  - DIFFERENT THINGS. Two notes. Each one's `## Definition` names the other and says in one sentence what separates them, with a link, so a reader who arrived at the wrong note leaves immediately rather than reading the wrong thing carefully. Neither note may claim the bare ambiguous word as an alias.
  - SPECIAL CASE. One is the other applied to a narrower setting. The general note lives in the domain that owns the general case; the specific note points `up` at it, or links to it with a phrase naming exactly what it specializes, and does not repeat the general note's definition.
  The failure this prevents is not a merge conflict, it is silence: two notes describing different things under the same word, neither aware of the other, both looking correct in isolation.
- Aliases are globally unique across the vault. Obsidian resolves a link by name, so two notes claiming one alias makes one of them unreachable under that name with no warning and no error. Before any packet is dispatched, check every seed alias in every packet against every title and alias already in the vault, and against the other packets. A word that is ambiguous on its own is not an alias for anybody: it is qualified in both places or dropped from both alias lists.

Work in six phases. Do not skip a phase and do not start writing files before the gate.

PHASE 1: STRUCTURE (subagents, in parallel, read only).
Launch two read-only exploration subagents at once and wait for both.

Subagent A, the vault contract. Have it read in full and report back, quoting rather than paraphrasing wherever a rule is exact: `__Meta/Quality-Bar.md` (the whole file, it is the spec), `README.md`, `Home.md`, `Notation.md`, `__Meta/Callouts.md` (only the list of callout types), every file in `__Meta/templates/`, and `.obsidian/types.json`. Its report must contain: the frontmatter contract per note_kind, the required section headings per note_kind verbatim, the three rungs of `## Formal statement`, the fixed discharge string for the bottom rung and where in the section that string goes, the hyperparameter test, the disqualification list, the heading rules (no H1 under `Knowledge/` and none on a chapter note, H1 on a container note and on any document read front to back, `##` for required sections, `###` for subsections), the rule against headings that name a source, whether a Bases query block is part of the required shape of an `index` and whether the list heading of an index is fixed or named for what it lists, the discharge available to `## Implementation` in a domain with no pinned library, and what the file says about adding a new note_kind and when that question reopens.

Subagent B, the vault as it stands. Have it produce: the full tree of `Knowledge/` and `Sources/` with one line per file giving path, note_kind, `up`, and `confidence`; the complete text of every domain hub under `Knowledge/`, meaning the `index` note whose `up` is `[[Home]]`, including each one's Areas list and What is missing list; the complete text of the exemplar chapter note named in the parameters; the output of `git log --oneline -n 12`, and then `git show --stat` on the most recent commit that integrated a chapter, as the exemplar of what a chapter integration touches (new notes, the hub, Home, the container note, and backfilled `sources:` and `up:` on existing notes); and, when the domain status is FIRST RUN, additionally `git show --stat 5a1a0c2`, the commit that created the `Mathematics` and `MLOps` domains, as the exemplar of what starting a domain touches. Also have it report every line anywhere in `Knowledge/`, `Sources/`, `Home.md` and `README.md` that mentions the chapter being integrated, the book being integrated, or the subject domain by name, because each one is a promise this run must keep or correct; every `[[wikilink]]` target in the raw file that does not resolve to an existing note; and every existing note whose title or `aliases` collide with a term in the raw file, which is the input to the collision rule above. Finally, have it report which existing notes end with a Bases query block and which do not, so new notes can follow the pattern of their neighbours rather than invent one.

Do not proceed until both reports are in. Keep both reports in your context for the rest of the session.

PHASE 2: READ THE RAW NOTES (you, personally, in full).
Read the raw file from the first line to the last with no offset and no limit. If the file is long, read it in consecutive chunks until you have seen the final line, and say the final line back to yourself so you know you reached it. Do not delegate this. Do not summarize it yet.

Then read, yourself, every exemplar note named in the parameters, and the exemplar chapter note, so you know what a finished note looks like in each shape you will be producing.

PHASE 3: INVENTORY AND PLAN (you, personally).
Build the plan in this order and write it to a scratch file outside the vault, not into the vault.

Step 3a, the inventory. Split the raw file into atoms. An atom is the smallest piece that lands in one place: usually one heading with its bullets, sometimes a single bullet, a single table, or a single code block when its siblings go elsewhere. Number the atoms in file order. Every line of the raw file belongs to exactly one atom. Tables, figures and code blocks that only reproduce an exhibit from the source are still atoms; they are allowed to be dropped, but only by an explicit decision with a reason.

Three shapes of atom need naming before they are missed. A heading with nothing under it is an atom, and its disposition is a decision: either the chapter covered it and I did not write it down, in which case the plan says so and the material is researched or deferred, or it is a stub for a later reading session, in which case it is dropped with that reason. A term listed with an empty definition is an atom, and the first place to look for its definition is later in the same raw file, where a term glossed in one line at the top is often developed in full under its own heading further down; when nothing in the raw file defines it, the note is still owed a definition, which comes from research and is reported as an addition rather than quietly written as though I had said it. A bullet whose content is a bare cross reference, with no claim of its own, is an atom whose disposition is a link rather than a note.

Step 3b, the destination table. One row per atom: atom number, raw heading, action, target path, note_kind, `up`, what this atom contributes, and why here. Actions are exactly one of: CREATE a new note, AMEND an existing note (say which section), RENAME or MOVE an existing note (old path to new path), DELETE an existing note (with the reason and where its content goes), DROP the atom (with the reason). A raw atom may feed several rows, since one passage often carries both the definition of a thing and a claim about a different thing it is being contrasted with. Every unresolved `[[link]]` from the Phase 1 report must appear as a CREATE row or the plan is incomplete.

Step 3c, the structural decisions. Decide and write down, with the reason, every placement question the chapter raises, checked against the Areas list of the domain hub and against the folder rule (the folder says what kind of thing a note is, `up` says what it is part of). Do not add a new note_kind. Every decision here is a decision about where things go and what earns a note, never a decision about what is true.

Step 0 of this step applies only when the domain status is FIRST RUN, and when it applies nothing else in the plan is settled until it is. Read the domain hub named in the exemplars first, because it is the precedent: it was started from a single chapter of evidence, it opens with a paragraph saying what earns a place in the domain and what does not, it has an Areas list whose entries are folders with the notes in them named in prose, and it has a What is missing list that is blunt about how little is there. Then decide and write down, with the reason:

- The domain's name and folder, and the hub note's path, which is the folder name repeated as the filename, matching `Machine Learning/Machine Learning.md`.
- The membership rule, one paragraph: what earns a place in this domain, and what looks like it belongs but goes to a neighbouring domain instead. Write this as that hub writes it, as a boundary against the neighbours rather than as a description of the subject. This paragraph is the thing that stops the next five chapters from being filed by accident, so it is worth more effort than anything else in this step.
- The folder taxonomy, with the evidence for each folder drawn from the atoms in the inventory and named atom by atom. One chapter is thin evidence, so the default is few folders. A folder is earned by holding notes this run actually produces, not by naming a topic the book will reach later; a topic with one note and a promise of more is a note at the top level of the domain, and the folder arrives with the second note. State plainly which folders are being created on one note of evidence and why that one note could not sit at the top level instead.
- Which atoms are not domain material at all. A chapter that opens a subject typically carries organizational material, meaning who does which job and what the teams are called, and it carries vendor and product names. Decide whether each of those is a note, a line inside another note, or a drop, and if the organizational material is a note, decide whether this domain or a neighbouring one owns it.
- The hub note itself: `note_kind: index`, `up: "[[Home]]"`, no H1, a scope paragraph, `## Areas` rather than `## Methods`, a Bases query block if the Phase 1 report says the index shape carries one, and `## What is missing` written honestly about a domain that is one chapter old.
- The line in `Home.md` under `## Domains` that introduces the domain, in the shape of the lines already there, and whether `README.md`'s layout table needs the domain named too.

The rest of step 3c applies to every run. At minimum decide: which atoms become notes at all, given that a term the chapter merely names in passing is a line in another note rather than a note of its own, and say which terms you are refusing a note to and why; for each note, whether it is a `concept`, a `method` or an `index`, checked against the concept and method test in section 2 of the quality bar (a method is something you carry out as itself and that changes something downstream, or an ordered protocol whose reading depends on the order; everything else is a concept) and against the rule that `index` is earned by having members to list and that a topic with none is a `concept` carrying its own definition; whether any existing note should convert between kinds under that same rule; which notes are paired contrasts that want the optional `## VS` section rather than two notes each describing the other; which atoms touch a neighbouring domain, and for each one whether the existing note there is amended and linked or whether this domain owns a genuinely different thing under a similar name; and whether a dataset note is required, given that the quality bar wants one per dataset a chapter works on. Where a decision contradicts a promise an existing note made, say which promise is kept and which is corrected, and never leave both standing.

Also produce, as its own table, the collision ledger: one row per term in this chapter that matches an existing note's title or alias, whether the parameters named it or Subagent B found it, giving the term, the existing note, the new note or amendment, the verdict of SAME THING, DIFFERENT THINGS or SPECIAL CASE, and the exact sentence each side will carry to tell itself apart from the other. A term with no row is a term nobody checked.

Do not reach for a new note_kind. The quality bar says when that question reopens, and the answer is never "during an integration run". A note that fits no existing kind comfortably is written to the kind it fits least badly and the strain is recorded in the final report and in the relevant index's What is missing, which is the evidence a kind is eventually argued from.

One decision is larger than placement and gets its own line in the plan when it arises: whether this run's material argues for restructuring an existing domain rather than only adding to one. A domain that turns out to be a special case of something this chapter introduces is a real finding and is allowed to move. It is proposed at the gate with its cost named in full: every file that moves, every `up` that changes, and every sentence in `Home.md`, `README.md` and the other hubs that names the old path in words, since wikilinks survive a folder move and prose does not. Never restructure silently and never as a side effect of a packet. Where the cost is small today and grows with every chapter, say so plainly, because that is an argument for doing it now rather than an argument against doing it at all.

Step 3d, the promises. For every line the Phase 1 report found that mentions this chapter, this book, or this subject, write the exact edit that retires the promise. At minimum this covers: the container note, whose plain text chapter line becomes a link; `Home.md`, whose Sources line records which chapters of this book are extracted and whose Domains list records the domain; `README.md`'s layout table, which counts the sources and the domains; the domain hub's Areas paragraphs and its What is missing list; and every note in a neighbouring domain that names this subject or promised this material. Add any others the report found. A promise that this run cannot keep is rewritten to say what is actually true, not left to rot.

Step 3e, the chapter note. Plan the chapter note at the path in the parameters, from `__Meta/templates/Note Kinds/Source (Chapter).md`: frontmatter with `note_kind: source`, `medium: book`, `chapter:` as the number from the parameters, `up:` as a link to the container note, `url:` from the parameters, and aliases for the chapter number and the chapter title. Then `## Thesis`, `## Extracted` grouped by theme with a group for notes amended rather than produced and a group for hubs and indexes revised, and `## Open questions`. It takes no H1. Also plan which open questions in earlier chapter notes, of this book and of any other, this chapter settles or partly settles, and what edit records that.

Step 3f, the research list. For every claim in the raw file that is uncertain, marked with a question mark, internally inconsistent, or likely wrong, write a research item: the claim, what to check, and which primary source settles it, using the ordering in the parameters. Do the same for every named system, product, service, protocol or standard in the raw file: what it is, who makes it, whether it still exists under that name, and whether the property the raw file attributes to it is true of it today rather than at the time some older source described it. A product list in the raw file is a research item in its own right, because product lists go stale faster than anything else in a note, and a list that was right when the book went to press may not be right now. Where the raw file carries formulas, every one gets rederived or checked against a reference; where it carries none, this clause is discharged and an arrow or an inequality used as shorthand in prose is not a formula.

Step 3g, the work packets. Group the destination rows into packets such that no file appears in two packets, and packets are independent of one another. Then fix, before any packet is dispatched, the final title of every note that will be created or renamed, because every packet links to notes owned by other packets and the link text must already be right. Each packet contains: the atom text verbatim, the target file or files and the action on each, the note_kind and its exact required sections from the Phase 1 report, `up`, a seed list of aliases (every name a person would type in a link, including plurals, abbreviations, the expansion of every acronym and the acronym of every expansion, and the name any widely used system gives the thing), the outbound links this note must make and the phrase that explains each relationship, the notes elsewhere that will link back to it, the research items that belong to it, the exemplar note to read first, and the style rules from the hard rules above. Every packet also carries: "Do not touch any file not named in this packet. Do not run git write commands. Report back before finishing."

Write the plan as: the destination table, the structural decisions with reasons, the promise edits, the chapter note outline, the research list, and the packet list. Then present it to me in full.

GATE: Stop here and wait for my explicit approval of the plan. Apply any changes I ask for to the plan before continuing. Do not write any file inside the vault before I say go.

PHASE 4: EXECUTE (subagents, in parallel where packets are independent).
Dispatch every packet to its own writing subagent. Independent packets go out together in one batch. A packet that amends a file another packet creates waits for that packet to finish. When the domain status is FIRST RUN, the packet carrying the domain hub goes last, because it describes what the other packets actually produced. Each writing subagent, in this order:
1. Reads `__Meta/Quality-Bar.md` and the exemplar note named in its packet.
2. Reads every existing note it is told to link to, so the link phrase is true and the `up` chain is consistent.
3. Does the research in its packet against primary sources, and records for each item: the finding, the source, and whether it confirms, corrects, or extends the raw notes. Research is for correctness and completeness. It is not licence to replace the raw file's wording with a source's wording.
4. Writes or amends the note to the contract for its kind. New notes get `confidence: draft`, never anything higher. Amended notes get this chapter appended to `sources:`, and the new material is merged into the section it belongs in by topic, sharpening or correcting what is there rather than being appended as a layer. A subsection is created only when the new material is a distinct sub-topic, and it is named for what it contains and never for where it came from. Where the new material contradicts what the note already says, the contradiction is settled by research and the note is rewritten to say one thing; two sections each asserting a different thing is never an acceptable outcome. A Bases query block is part of the required shape of an `index` and every new index gets one; on any other kind it is appended only where the note's neighbours in the same folder carry one.
5. Self-checks before reporting: every required section present and non-empty, `## Where it is used` has at least two outbound links each carrying its relationship phrase, every quantitative claim has a formula somewhere in the note, the discharge string is exact and last in its section if used, no H1 on a note under `Knowledge/` and none on a chapter note, no heading that names a source, no bare "the chapter" or "the book" as a subject in the prose, no dash characters of either kind, no "e.g.", no placement commentary in the body, frontmatter keys spelled exactly, `up` is a link and is never `[[Home]]` for a leaf.
6. Reports back with: files written or changed, with a one-line summary each; every fact in the raw notes it corrected, with the raw wording, the corrected wording, and the source; every claim it added that the raw notes did not contain, with the source; every raw bullet it suspects was pasted from elsewhere rather than written by me, with the raw wording; every research item it could not settle, stated as uncertain rather than guessed; and any deviation from its packet with the reason. A typing slip is not a correction. A misspelling, a transposed word, or a word the surrounding sentence plainly contradicts is fixed silently and listed in one short line at the end of the report, separately from the corrections, so that the corrections section stays a list of places I understood something wrongly rather than a list of places I typed badly.

Keep every report. You will need them in Phase 6.

PHASE 5: VERIFY (you, personally, with scripts where possible).
Run these checks over the whole vault and fix what fails, either yourself for one-line fixes or by sending the owning subagent back for anything larger:
- Every `[[wikilink]]` in `Knowledge/`, `Sources/`, `Home.md` and `README.md` resolves to an existing file, allowing for `|alias` display text and `#heading` suffixes.
- Every note under `Knowledge/` has `note_kind`, `up`, and (where its kind requires them) `aliases`, `sources`, and `confidence`, with the keys spelled exactly. Every `up` value resolves.
- Every new or amended note carries the required `##` sections for its kind.
- No note under `Knowledge/` carries an H1, and neither does any chapter note. Container notes, dataset notes, `Home.md`, `README.md`, `Notation.md` and the files under `__Meta/` do carry one, and this check must not strip it.
- No note under `Knowledge/` carries a heading that names a source, and none uses "the chapter" or "the book" as a bare subject in its prose.
- No file under `Knowledge/`, `Sources/`, `Home.md` or `README.md` contains an em-dash, an en-dash, or the string "e.g.".
- Every note the chapter produced or amended is listed under `## Extracted` in the chapter note, and every note listed there exists and names the chapter in its `sources:`.
- Every promise line from Phase 3d is gone or rewritten.
- No alias appears on two notes, and no note claims an alias that is another note's title. Collect every `aliases` entry and every filename across the vault and check for duplicates mechanically, since this failure is silent in Obsidian and invisible on inspection.
- Every row of the collision ledger landed: the verdict was applied, and where the verdict was DIFFERENT THINGS both notes actually carry the distinguishing sentence and the link.
- The container note links the chapter, `Home.md` counts it, and `README.md`'s layout table counts it. When the domain status is FIRST RUN, `Home.md` also introduces the domain and the hub's Areas list names every folder the run created.
- Every atom in the inventory is accounted for: walk the destination table row by row and confirm the content actually landed where the row says, in substance, not just by file existence. An atom marked DROP has its reason in the plan.
- `git status --short` shows only the files the plan named. Anything else is a mistake to reverse by hand, never with a git command.

PHASE 6: EMPTY THE RAW FILE AND REPORT.
Only when every check in Phase 5 passes, truncate the raw file to zero bytes. Do not delete it and do not move it. Then give me the final report, which has exactly these parts:
1. A table of every file created, amended, renamed, moved or deleted, one row each, with the reason in a few words.
2. Structural decisions taken, one line each, with the reason. When the domain status was FIRST RUN, the domain's membership rule and the evidence behind every folder created come first, because they are the decisions I will be living with for the rest of the book. Any restructuring of an existing domain is stated here in full, with what moved and what prose was rewritten to match.
3. The collision ledger as it was finally resolved: term, the notes on each side, the verdict, and the sentence each note carries. Include the collisions you found that the parameters did not name, and the forward collisions you declined to act on, with what will trigger them.
```
