## Definition

Production machine learning is the setting a fitted model works in once it serves live traffic on behalf of somebody who is waiting on the answer, as against the research setting, where the same model is scored on a dataset that does not move and nobody is waiting on anything. Nearly every engineering priority inverts between the two, so a model that wins in one setting is not thereby a model worth running in the other.

## VS

The axis is what the model is being asked for. Research asks for the highest number on a fixed dataset. Production asks for an answer that several parties with different stakes in it can all live with, computed on data that keeps moving. [[DMLS Ch01 Overview of Machine Learning Systems|DMLS chapter 1]] draws the comparison across five rows, restated here.

| Property               | Research                                                                                             | Production                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Requirements           | one agreed score on a shared benchmark dataset, pushed as high as anyone has managed                 | several parties each want something different, and all of them have to be satisfied at once |
| Computational priority | a fit that finishes soon, on hardware kept saturated with training examples                          | one prediction returned soon, to the one caller blocked on it                      |
| Data                   | fixed, and reused unchanged by everyone reporting on it (the moving case is its own research subfield, continual learning) | shifting continuously while the fitted model stays as it was                       |
| Fairness               | rarely part of what is scored                                                                        | has to be accounted for                                                            |
| Interpretability       | rarely part of what is scored                                                                        | has to be accounted for                                                            |

Both columns of the computational priority row are about speed, and not about the speed of the same thing. Research is paid for a trained model, so what gets optimized is how long a fit takes and how many training examples per second the hardware will absorb, its throughput. Production is paid for an answer, so what gets optimized is the latency of a single prediction, the interval between a request arriving and a result going back, with a caller blocked for the duration. Inference is the part being timed in the second case, the forward pass turning one input into one prediction, not the fitting that produced the weights. The commitment is the same shape as the one [[Online Transaction Processing]] makes, interactivity with no particular number of milliseconds attached: what counts as fast is set by whoever is waiting.

That row is narrower than it looks, because a whole regime of production inference has no waiting caller in it. Batch serving is a first-class mode on every major platform rather than a marginal one: batch transform and asynchronous inference on Amazon SageMaker, batch inference on Google Vertex AI, batch endpoints on Azure Machine Learning, each a managed job that scores an accumulated input set and writes the results somewhere instead of answering anybody, and each documented in terms of not needing an immediate response. Azure states the selection criterion as plainly as it can be stated, that you reach for a batch endpoint when you have no low latency requirement. The large-model providers sell the trade at a published price: OpenAI's Batch API, Anthropic's Message Batches API and Google's Gemini batch inference all charge exactly half the synchronous rate in exchange for a turnaround window of up to twenty four hours. Benchmark vocabulary encodes the same split and predates the comparison above: MLPerf Inference, run by MLCommons, sends its Offline scenario every sample at once, applies no latency constraint at all, and scores throughput, while its Server scenario draws arrivals from a Poisson process and holds the system to a benchmark-specific bound on a tail percentile. Even there the reported number is the highest arrival rate sustainable within that bound, which is a throughput maximized subject to a latency constraint rather than a latency minimized. So the accurate form of the row is that production optimizes latency where a caller is blocked and throughput or cost per prediction where none is, and that serving stacks now expose the trade as a knob: Triton's dynamic batcher holds requests in the queue for a configured delay precisely to spend latency on throughput, and continuous batching, introduced as iteration-level scheduling in Orca and carried into vLLM alongside PagedAttention, reports its gains as multiples of throughput at an unchanged level of latency.

Two rows name properties a table cell cannot define, and both are new vocabulary here. **Fairness** in the algorithmic sense is usually construed as the absence of discrimination: a system's predictions must not depend improperly on a protected attribute such as race, sex or age. What it is not is a single test. Barocas, Hardt and Narayanan reduce the many proposed formalizations to three observational criteria, independence, separation and sufficiency, prove them pairwise incompatible outside degenerate cases, and hold that none of the three is both necessary and sufficient, so a system can satisfy one and still be plainly unfair (*Fairness and Machine Learning*, MIT Press 2023). The obstruction is a theorem rather than an engineering difficulty: calibration within groups, held alongside balanced average scores for the positive and the negative class, forces either equal base rates across the groups or perfect prediction (Kleinberg, Mullainathan and Raghavan 2016), and a calibrated score cannot equalize false positive and false negative rates between groups whose prevalence differs (Chouldechova 2017). Choosing a criterion is therefore choosing which unfairness to accept. One trap belongs with that, and it is a vocabulary trap rather than a technical one. Everywhere "fair" already appears in these notes, a fair die, a fair draw, a fair comparison between a penalized model and an unpenalized one, a fair price charged by a regularization term, it carries the everyday sense of an unbiased comparison or an unbiased draw. The algorithmic sense above is new vocabulary here and is a different word that happens to be spelled the same, so neither reading may be substituted for the other.

**Interpretability** is the degree to which a system's behaviour can be presented to a person in terms that person understands, the definition proposed by Doshi-Velez and Kim in "Towards a Rigorous Science of Interpretable Machine Learning" (2017), who trace the need for it to an incompleteness in how the problem was formalized, meaning the score being optimized leaves something that still has to be checked by hand. The term is not settled: Lipton's "The Mythos of Model Interpretability" (2016) argues it is not a monolithic concept but several distinct ones, separating transparency, whether the mechanism itself can be followed, which he splits again into simulating the whole model, making sense of its individual parts, and understanding the training algorithm, from post-hoc interpretability, whether a trained model can be made to emit explanations after the fact. His conclusion is the usable one: an assertion that something is interpretable says nothing until it fixes which notion it means. Neither term has a note of its own yet; both are owed one from DMLS chapter 11, on the human side of machine learning.

The data row is the one that already has a research response attached to it. A research dataset is fixed, and being fixed is exactly what makes a number reported on it comparable with another number reported on it; production data shifts while the fitted model stays put. Research does work on the shifting case, and that subfield is [[Continual Learning]], where a model goes on being updated from data that arrives after it shipped. The same shifting seen from the production side has a name for what it costs, [[Model Rot]]: the decline of a deployed model as the distribution moves away from the one it was fitted on, with nothing in the system breaking while it happens.

The requirements row rests on what a benchmark dataset is and is not. Its whole value is that it is fixed and split the same way for everybody, so two reported scores can be set side by side, and [[Open Data Repositories]] records which sources work that way and which have drifted. The limit follows immediately: a leaderboard position is evidence about the benchmark, since a deployment has no canonical split, no fixed population, and usually no single number that every party involved has agreed to be ranked on. The Netflix Prize is the worked case, a contest scored purely on predictive accuracy by one measure, after which most of the effort that moved the leaderboard never reached the production recommender; Barocas, Hardt and Narayanan give it as what overfitting to a problem formulation looks like. The requirement a benchmark cannot express is the one Breck and colleagues make a test in its own right in their production readiness rubric: that the offline proxy being optimized is actually known to correlate with the online impact the system will be judged by.

## Formal statement

The two settings differ in the structure of the objective, not merely in how hard the objective is to reach.

Research fixes a dataset and a single scalar score on it. A real-valued objective ranks candidates completely: given any two systems, one scores at least as high as the other, so the relation is a total preorder, complete and transitive, with ties allowed and incomparability impossible. "Better" is therefore well defined with no further argument, and a leaderboard is possible, a leaderboard being that ordering written out.

Production replaces the single scalar with a conjunction of requirements held by different parties, and a conjunction of requirements is not a scalar. Two or more objectives that are not collapsed into one number admit only Pareto dominance as an ordering: one objective vector dominates another when it is at least as good in every component and strictly better in at least one. Dominance is a strict partial order on those vectors, irreflexive, asymmetric and transitive, and, unlike the scalar case, not complete. Lifted back from vectors to the systems that produced them it is weaker still, since two different systems sharing an objective vector are indistinguishable to it. Two candidates that each beat the other somewhere are therefore incomparable, and no further measurement of either makes one of them better. What such a problem has is therefore not an optimum but a set of them, the non-dominated candidates, whose image in objective space is the Pareto frontier (Miettinen, *Nonlinear Multiobjective Optimization*, 1999). Picking one member of that set requires a preference between objectives supplied from outside the optimization, which is to say a judgement about whose requirement outweighs whose.

The practice has a standing device for recovering a total order anyway: fix a threshold on every requirement but one and maximize the remaining one subject to those thresholds. Ng names the two roles satisficing metrics and an optimizing metric (*Machine Learning Yearning*, a self-published draft rather than a reviewed text, and satisficing is Simon's word from 1956), and the manoeuvre is the epsilon-constraint method of multi-objective optimization under another name. It works, and it works by making exactly the outside judgement named above, since the thresholds are chosen rather than derived. Nothing in the problem supplies them.

The claim is falsifiable in the ordinary way. It predicts that in production you can be handed two candidate systems with every number measured and still have no fact of the matter about which is better, and that is what happens every time a faster model is also a less accurate one. The five rows above are five instances of this one difference, not five separate observations.

## Where it is used

[[MLOps]] is the practice this setting creates the need for, everything done to a model because it is now answering rather than being built. [[DevOps]] is the same setting for a system whose behaviour was written by hand instead of learned from data, and it already states what operating a learned system adds that operating an ordinary service does not.

[[Machine Learning System]] is what is actually being operated here, code plus training data plus the artifact fitted from the two, which is why a deployment has three things to pin rather than one. [[Model Rot]] is the standing failure mode of the setting, the cost of the data row, and [[Continual Learning]] is the response that keeps fitting after deployment instead of accepting the decline.

[[Machine Learning Applicability]] is where the price of all of this is weighed before anything gets built: its eighth condition, that the problem occurs at scale, names the volume of predictions the up-front investment has to be amortised across, and this setting is where the amortising actually happens. [[Open Data Repositories]] holds the benchmark sources the research column is scored on. [[Generalization]] is the assumption the research column leans on and the production column tests, since a score estimated on a [[Testing Set]] is a claim about unseen data, and production is where that claim meets data nobody curated.
