## Definition

Continual learning is the practice of keeping a deployed model updated from data that arrives after it shipped, together with the research problem that practice immediately runs into: adapting to the newest data without destroying what the model already knew. Those are one subject rather than two layers. A system whose world keeps moving has to keep learning, and a system that keeps learning on whatever arrived most recently overwrites knowledge it is still being asked to use.

The limiting case shows how far the practice reaches. A model can be put into service having been trained on nothing at all, learning entirely from the traffic it serves, which makes continual learning one of the recognised routes around the requirement that training data exist before a project starts. The data it is eventually fitted on is generated by the running system rather than assembled ahead of it, so the requirement is satisfied afterwards instead of in advance.

## VS

Continual learning is a production practice, a deployed model that goes on being updated from live data, and it is usually carried out by retraining on a schedule rather than by [[Online Learning]], which is a fitting regime and answers a different question: how many instances one parameter update consumes. The two come apart in both directions, which is the proof that they are separate questions. A continual-learning system is most often implemented as a scheduled retrain over accumulated data, which is [[Batch Learning]] doing the fitting and not online learning at all; conversely, an online fit run over a fixed dataset that is simply too large for memory is [[Out-of-Core Learning]], which updates one mini-batch at a time and is not continual learning, because nothing in it is deployed and no new data is arriving.

Where continual systems do update frequently, they still update in micro-batches of a few hundred to a few thousand instances rather than on every single instance, and the reason is the failure named below: a neural network fitted on one instance at a time forgets fastest.

## Formal statement

The setting is a model $h_{\boldsymbol\theta_t}$ updated on a cadence from data arriving after deployment, so the distribution it is fitted to is indexed by time rather than fixed: the update at step $t$ draws from $p_t(\mathbf{x}, y)$, the sequence $p_1, p_2, \dots$ is non-stationary, and neither the number of updates nor the number of distinct regimes is known in advance. That last clause is what separates the setting from a fixed dataset consumed in pieces, where the distribution is one and the pieces are an implementation detail.

What is wanted guaranteed has two halves: after the update at $t$, loss on $p_t$ falls, and loss on the earlier $p_1, \dots, p_{t-1}$ does not collapse. Only the first half comes for free. Fitting $\boldsymbol\theta_t$ on data from $p_t$ alone drives loss on the earlier distributions up abruptly rather than gradually, and that failure is **catastrophic forgetting**, which is the standard name for it (coined as catastrophic interference by McCloskey and Cohen in 1989, and current in both wordings since French's 1999 review).

Stated this way the setting is the stability-plasticity trade-off raised to the level of a deployed system: how far the system must be plastic enough to integrate new information against how far it must be stable enough not to overwrite consolidated knowledge. [[Learning Rate]] already carries the same trade-off at the level of one step size, where it is exact, a single $\eta$ that fixes both how fast the fit moves and how many past instances it effectively remembers. At system level there is no single number to read it off: the knobs are the update cadence, how much older data is replayed alongside the new, and whether an update resumes from the previous parameters or starts from scratch.

**Not further quantitative at this depth.**

What would turn this into arithmetic is the cost side of those knobs, which DMLS chapter 9 is named for and supplies: how often an update is worth running against how fast the distribution is moving, and what one update costs when it resumes from the previous parameters rather than refitting from nothing. The measures the research literature uses to check the second guarantee, which score the model on every earlier distribution after every update, belong with it.

## Where it is used

[[Model Rot]] is the condition this exists to answer: a fixed model decays because the production distribution moves away from the training one, and continual learning is the standing response to that decay rather than a one-off repair. Either fitting regime can carry it out, which is the whole point of keeping the two questions apart: [[Batch Learning]] carries it as a scheduled retrain on accumulated data, and [[Online Learning]] carries it as a running update per instance or mini-batch. [[Out-of-Core Learning]] is the case that shows the two come apart, being an online fit with no deployment anywhere in it.

It belongs to [[MLOps]] rather than to model building, since it only means anything once there is live traffic and a clock, and it is one of the things that makes [[Production Machine Learning]] harder than shipping a fixed artifact: the model is a moving object with a cadence, a rollback path, and an evaluation that has to be repeated every time it moves. [[Machine Learning Applicability]] names it as the route around the condition that data must exist before a project starts, since a model can ship untrained and learn from what it serves. [[Learning Rate]] is where the same stability against plasticity trade-off is carried at the level of a single step.
